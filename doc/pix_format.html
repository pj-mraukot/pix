The PIX image format

A lossless format for 24-bit RGB images, with two compression algorithms that share a single file header.

Overview

A PIX file holds one image of 8-bit R, G and B samples, with no alpha channel. An image with transparency has to be flattened, for example onto a white background, before it is encoded. The image is compressed with one of two algorithms, which the header names. A decoder reads both.

Algorithm 1 A1

Nibble codes, then zlib.

  • 16×16 blocks, each with its own cache of 80 colours; a global cache holds 8192 more
  • Each pixel gets the shortest code that fits: a repeat, a run, the pixel above, a cache slot, a MED residual or a literal colour
  • The nibble stream is deflated with zlib
  • Fast to encode and very fast to decode

Algorithm 2 A2

Prediction and adaptive binary arithmetic coding.

  • Pixels are coded row by row, with no blocks
  • Each pixel is one of up to 9 candidate colours, a colour from a list of 16384 recently used colours, or three residuals against a blended prediction
  • Every decision is a context-modelled bit, so a well-predicted pixel costs a fraction of a bit
  • Typically about a quarter smaller than algorithm 1, but much slower; decoding costs as much as encoding

Algorithm 1: nibble codes and zlib A1

RGB image→ pad to whole 16×16 blocks→ one nibble code per pixel or run→ pack 2 nibbles per byte→ zlib (level 9)

The encoder writes the image as a stream of 4-bit nibbles. Each pixel, or each run of pixels, becomes one code of 1 to 7 nibbles. The encoder always picks a short code that describes the pixel exactly. zlib then removes much of the repetition that remains in the stream.

  • Nibbles are packed high nibble first. If the count is odd, the last byte is padded with a 0 nibble.
  • Numbers made of several nibbles (XX, XXX, RRGGBB, a cache distance) are stored most significant nibble first.
  • The stream ends with 00 after the last block.

Blocks, pixel order and padding

The image is processed in 16×16 blocks. Blocks go left to right, top to bottom, and the pixels in each block go row by row, left to right:

for (Y = 0; Y < paddedHeight; Y += 16)
    for (X = 0; X < paddedWidth; X += 16)
        processBlock(X, Y);       // 256 pixels, row by row

If the width or height isn't a multiple of 16, the encoder pads the image to whole blocks. Each row's last pixel is repeated to the right, and the last row is repeated downwards. The padding is coded like any other pixels. The header keeps the original size, so the decoder decodes the padded image and keeps only the original area.

Blocks only decide which cache1 is in use and where runs may end. A run never crosses a block boundary. Prediction, the pixel above and the colour history all work across block boundaries.

The encoder and decoder keep the same state and update it the same way after every code.

A prediction run predicts each pixel only after the previous one has been placed. In a flat area, or along a straight vertical edge, one 0E NN code can therefore place hundreds of pixels.

Prediction and residuals

The predicted colour P uses the MED predictor from JPEG-LS, applied to each channel separately. Its inputs are the already decoded pixels to the left (a), above (b) and above-left (c):

if (c >= max(a, b))      P = min(a, b);    // an edge above or to the left
else if (c <= min(a, b)) P = max(a, b);
else                     P = a + b - c;    // a smooth gradient

At the image edges: pixel (0,0) is predicted as black, the rest of the top row as the left pixel, and the rest of the left column as the pixel above.

Residuals are taken after a green transform, because the differences of R and B usually follow the difference of G. All arithmetic is modulo 256, with values wrapped to −128..127:

encode:  dG = G − P.g        dR = (R − P.r) − dG        dB = (B − P.b) − dG
decode:  g = P.g + dG        r = P.r + dG + dR          b = P.b + dG + dB      (each & 255)

A uniform brightness change, such as a grey gradient, gives dR = dB = 0. The residual codes pack the three values as follows:

CodeValue vUnpacking
0X n, X = 4..76 bits: (X−4)<<4 | ndG = (v>>4) − 2, dR = ((v>>2)&3) − 2, dB = (v&3) − 2
D G R Bthree nibblesEach nibble is a signed two's-complement value, −8..7
0X nnn, X = 8..913 bits: (X−8)<<12 | nnndG = (v>>8) − 16, dR = ((v>>4)&15) − 8, dB = (v&15) − 8
0X nnnn, X = A..D18 bits: (X−A)<<16 | nnnndG = v>>10 (taken mod 256), dR = ((v>>5)&31) − 16, dB = (v&31) − 16

The residual and prediction codes update the colour history like any other code: a run updates it once for each pixel it places. They never change cache1 frequencies.

The two caches

cache1: 80 colours per block

  • Lookup (codes 5X–9X): adds 1 to the slot's frequency. Codes 1 and 2 also add 1 when their colour is in cache1, and runs 3X/4XX add the whole run length. Codes A, B, E, F and the residual codes never change frequencies.
  • Insertion (code C):
    1. Search slots slotIndex..79 for the smallest frequency. An unused slot counts as smaller than any frequency, and a tie goes to the lowest slot.
    2. If that slot is used, its colour moves to cache2, unless cache2 already has it.
    3. Write the new colour with freq = 1, then set slotIndex = (slotIndex + 1) % 80. Starting the search at slotIndex keeps the low slots from being overwritten again and again.
  • Block start: the encoder scores the final cache1 of each of the previous 4096 blocks by how many of its colours appear in the new block. It picks the best score above 0, and the nearest block on a tie. It then writes 01 L DIST, where DIST = 0 means the previous block, and uses the minimal L. The copy's frequencies are divided by 4 and its slotIndex is reset to 0; slots whose frequency drops to 0 stay in use. If no block is selected, there is no instruction and the block starts with an empty cache1.

cache2: 8192 colours for the whole image

Code E and colours pushed out of cache1 are written at cache2's slotIndex, which then advances by one modulo 8192. Codes A XXX and B XXX read a slot.

Encoder choices

These rules are not part of the format, and a different encoder could choose differently. They decide only how well the image compresses. For each position in a block:

  1. If the colour is the last colour, use a run of it (1, 3X, 4XX). But if a prediction run of at least 2 pixels is longer, use that (03 N, 0E NN).
  2. Otherwise, code a single pixel with the first of these that fits:
    1. next-to-last colour: 2
    2. same as the pixel above: F
    3. exact prediction: 02
    4. in cache1: 5X…9X
    5. the shortest residual code that fits: 04–07, D, 08/09 or 0A–0D; cache2 is used instead of the 5- and 6-nibble residual codes
    6. in cache2: A, B
    7. a literal: C if the colour appears at least 3 times in the rest of the block, otherwise E

Residual codes come before the caches because they compress much better under zlib. Neighbouring residuals are often alike, so zlib finds repeated byte patterns in them.

Some things to notice:

  • At (12,2) the white pixel above and the blue pixel above-left push the MED prediction to #FFDB9C. That is too far from the real colour for any residual code, so the colour is written as a literal.
  • The gradient gives the same 09 888 code eleven times, a repetition that zlib compresses well.
  • The 256 padded pixels take 119 nibbles (60 bytes). After zlib, the whole file is 64 bytes, a third of the 192 bytes of raw RGB.

The raw nibble stream, two nibbles per byte:

05 a3 fc 4a 90 d9 35 23 00 a5 4d a0 98 88 09 88 80 98 88 ... e6 a7 47 e0 98 88 ... 0d af 46 11 50 35 20 eb 10 00

Decoding

for each block (left to right, top to bottom):
    if the next nibbles are 0 1:  read L, read L nibbles of DIST
                                  cache1 = copy of finalCache[block - 1 - DIST], freq /= 4, slotIndex = 0
    else                          cache1 = empty
    i = 0
    while i < 256:
        read one code, which gives a colour c and a count n (1 for single pixels)
        a run must not cross the block's end (i + n <= 256)
        place n pixels; a prediction run predicts each pixel after placing the previous one
        update last / nextToLast, cache1 frequencies and the caches as described above
    finalCache[block] = cache1
read 00
crop the padded image to width × height

The decoder rejects these as a damaged stream, not as a crash: an empty cache slot, F in the top row, a run past the block's end, an unknown code, an impossible cache distance, or reading past the stream's end.

Algorithm 2: prediction and arithmetic coding A2

Algorithm 1 leaves part of the work to zlib, which knows nothing about images. Algorithm 2 models the image directly. Every decision is a binary event coded by an adaptive binary range coder, with probabilities chosen by the pixel's surroundings. A pixel the model expects costs well under one bit.

The encoder and decoder run the same model and make the same decisions in the same order: where the encoder writes a bit, the decoder reads it. All arithmetic the decoder depends on is integer, so a file decodes the same on every platform.

Data

After the 20-byte header (algorithm "A2", unpacked size width × height × 3) come:

  • the range coder's output;
  • a CRC-32 (zlib's crc32, 4 bytes, little-endian) of the decoded RGB bytes: rows top-down, R G B for each pixel. If it doesn't match, the decoder reports a damaged file.

There are no blocks and no padding. Pixels are coded row by row, left to right.

One pixel

The pixel's neighbours, as used throughout algorithm 2:

NN NWNNE WWWXlaterlater
  1. Predict each channel, G first, from a blend of five predictors plus a bias correction.
  2. Code the mode, i.e. how the pixel is described:
    • as one of up to 9 candidate colours: the predicted colour, colours that followed the same neighbourhood before, or the colours of six neighbours;
    • as an index into the list of recently used colours;
    • as residuals of G, R and B against the prediction.
  3. Learn: whichever way the pixel was coded, every model is updated with it: predictor errors, bias statistics, hash tables and the recent list.

Binary arithmetic coder

Probability model (BitModel)

Each model holds the probability that the next bit is 1, as a 16-bit fixed-point value. It mixes a fast-adapting estimate with a slow one:

target = bit ? 65536 : 0
fast  += (target − fast) >> 4
slow  += (count < 510) ? (target − slow) / (++count + 1)    // a plain average at first
                       : (target − slow) >> 9
p      = clamp((fast + slow) >> 1, 64, 65472)              // both start at 32768

The fast estimate follows local changes in the image. The slow one starts as the average of all bits seen so far, so a fresh model learns quickly, and later becomes a long-term average.

Range coder

The coder uses a 32-bit range with LZMA-style carry propagation. The encoder keeps 33 bits of low, a cache byte and a cacheSize.

bound = (range >> 16) × p
bit 1:  range = bound                       (decoder: code < bound)
bit 0:  low += bound;  range −= bound
while range < 2^24:  shift one byte out,  range <<= 8

The decoder starts by reading 5 bytes into code, and reads past the end of the data give zero bytes. The encoder flushes with 5 byte shifts.

Coding numbers

Numbers are coded bit by bit, each bit with its own model, in an Elias-gamma-like layout:

ModelRangeBits
ResidualModel−128..127
  1. zero flag (1 = zero; nothing follows)
  2. sign (1 = negative)
  3. n = |e| (1..128), with k = ⌊log₂ n⌋ coded in unary: bits exp[i] = 1 while i < k, then a 0 (omitted after 7 ones)
  4. the k bits of n below its top bit, high to low, each with model mant[k][position]
NumberModel1..16384The same without the zero flag and the sign; the exponent goes up to 14

Small values, the common case, cost only a few well-predicted bits. Every mantissa bit has its own model, so the coder also learns the shape of the distribution.

Channel prediction

Each channel c (values 0..255) is predicted from that channel of W, N, NW and NE. Missing neighbours are filled in: at x = 0, W = N (or 0 for the first pixel); in the top row, N = W; a missing NW or NE becomes N.

Five predictors, weighted by how well each did nearby

#PredictorGood for
0Whorizontal structure
1Nvertical structure
2clamp(W + N − NW)smooth gradients (a plane)
3clamp(W + NE − N)diagonal edges
4(W + N + 1) >> 1noise (averages it)

The absolute error of every predictor is stored for every pixel. Predictor i's weight comes from its errors at the neighbouring pixels:

s_i      = 2·err_i(W) + 2·err_i(N) + err_i(NW) + err_i(NE) + 1      // 0 outside the image
weight_i = 2^32 / s_i²                                              // integer, from a table
spatial  = (Σ weight_i · pred_i + Σ weight_i / 2) / Σ weight_i

A predictor that was exact around the pixel dominates the blend; one that missed counts for very little.

G first, then R and B follow G

Channels are coded in the order G, R, B. After G is known, its prediction error eG = G − predG is added to the spatial prediction of R and of B. If the pixel is brighter than expected in G, it is probably brighter in R and B too:

G:      base = spatial
R, B:   base = clamp(spatial + eG)

Activity and bias correction

Activity measures how busy the neighbourhood is: a = the sum of |residual| at W, N, NW and NE for the channel. Its bucket (0..15) is the number of limits in {0, 1, 2, 3, 4, 6, 8, 11, 15, 20, 28, 40, 56, 80, 112} that a exceeds.

Bias correction, as in JPEG-LS, removes systematic errors. The context is (channel, activity bucket, sign(W − NW), sign(N − NW)). It keeps a sum and a count of value − base, each sample clipped to −16..16; when the count reaches 64, both are halved (the sum rounded half away from zero). Then:

corr     = round(sum / count)            // 0 if count is 0
pred     = clamp(base + corr)
residual = (value − pred) wrapped to −128..127       decode: value = (pred + residual) & 255

Clipping the samples matters: without it, a single sharp edge would shift the predictions of the flat areas around it.

Each residual is coded with a ResidualModel chosen by the channel, the activity bucket, and, for R and B, the size of eG: 0, 1, 2–3, 4–7 or 8+.

Colour candidates

Text, icons and flat UI areas don't need residuals. Their pixels repeat colours seen nearby or earlier. Before any residual, the coder can name a whole colour from a short candidate list, built in this order. A candidate that is missing or equal to an earlier one is skipped, so the list holds up to 9 distinct colours:

#Candidate
0The predicted colour: the final predictions of R, G and B, with eG = 0
1The colour that followed the neighbourhood (W, N, NW, NE) last time, from a hash table of 220 entries
2The colour that followed the neighbourhood (W, N) last time, from a second table of 220 entries
3–8The colours of W, N, NE, NW, WW and NN (when missing: W = N or 0, N = W, NE and NW = N, WW = W, NN = N)
hash2 = ((W·0x9E3779B1) ^ (N·0x85EBCA77)) · 0xC2B2AE3D >> 12                                  (32-bit unsigned)
hash4 = ((W·0x9E3779B1) ^ (N·0x85EBCA77) ^ (NW·0x27D4EB2F) ^ (NE·0x165667B1)) · 0xC2B2AE3D >> 12
                                                         colours as 0xRRGGBB; after every pixel
                                                         both tables store its colour at these hashes

The hash tables are what make repeated text cheap. When the same letter shape appears again, the same neighbourhoods recur, and each one remembers the colour that came next.

Recent colours

The coder keeps a move-to-front list of up to 16384 distinct colours, most recently used first. After each pixel, its colour moves to the front; when the list is full, the least recently used colour drops off. Frequently used colours therefore keep small indexes, which cost few bits.

Coding mode

Each pixel's mode is stored, because the mode of W and N is part of most contexts: 0 = predicted colour, 1 = other candidate, 2 = recent colour, 3 = residuals. A missing W or N counts as mode 3. The bits are coded in this order:

any: 1 = the colour is a candidate.
context: G activity bucket; prediction equals W / N; W == N; N == NE; modes of W and N

if 1: one flag per candidate in list order, 1 = "this one". The last candidate needs no flag.

predicted colour context: G bucket; prediction equals W / N; modes of W and N
other candidates: candidate number; which of W==N, W==NW, N==NE, N==NW, W==WW, N==NN hold; whether this candidate had the colour of pixel W / of pixel N; modes of W and N

if 0: recent flag, 1 = the colour is in the recent list.
context: G bucket; modes of W and N

if 1: index + 1 as a NumberModel number; the model depends on W's mode. Candidates are skipped when counting, so index 0 is the most recently used colour that isn't a candidate.

if 0: residuals of G, R and B.

Encoder choices

The encoder estimates the cost of each option in 1/256 bits, from the current probabilities, using a table of −log₂ p. The decoder doesn't need to know these rules; it follows the coded decisions.

  • If the colour is a candidate, use it, unless coding the residuals is cheaper.
  • Otherwise, if the colour is in the recent list, use it if that is cheaper than the residuals.
  • Otherwise, code the residuals.

On the 16×4 example image, algorithm 2 coded 30 pixels as the predicted colour, 16 as another candidate and 18 with residuals. At 87 bytes it is larger than algorithm 1's 64 bytes, because such a small image gives the adaptive models too few pixels to learn from. On real images it is almost always smaller (see the comparison).

Comparison

Both algorithms are lossless and use the same header; they differ in how much work they spend on each pixel:
